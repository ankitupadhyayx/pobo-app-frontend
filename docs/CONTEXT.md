# POBO AA app: context

What is where, and what the domain words mean. Read `AGENTS.md` first for running, checks and hard rules.

## The wider system
| Part | What |
|---|---|
| This repo | Expo app for Area Ambassadors (AAs) |
| Backend (separate repo) | Django 5.2 + DRF + Postgres + Redis. API under `/api/v1`, Swagger at `/api/docs/`, schema at `/api/schema/`. The Django admin is the interim **Ops console** (supervisors, admin, finance) |
| Contract | `openapi.yaml`, generated by the backend into a sibling `../shared/` folder; the app's client is generated from it (`npm run api:gen`) |
| Website | Posts leads to `POST /api/v1/public/intake`; they are routed to an AA |
| CRM console | Planned later; not built |

Backend change log, requests between app and backend, and the founders' QA documents lived in the `shared/` folder, which is not part of this repo. The parts that matter are distilled in `docs/`.

Action sheets (call outcome, follow-up, transfer, escalation, referral, message, add requirement, complete requirement, visit sheets) are not routes. They are mounted once by `src/components/shell/ActionHost.tsx` and opened through `src/state/actions.ts`.

New route files need typed routes regenerated. Metro does it when running; otherwise run:
`EXPO_ROUTER_APP_ROOT=$PWD/src/app node -e 'require("@expo/router-server/build/typed-routes").regenerateDeclarations(process.cwd()+"/.expo/types")'`

| Component | File | Use |
|---|---|---|
| SuccessHost / SuccessSheet | `src/components/shell/SuccessHost.tsx` | Global success feedback. Call `useActions().showSuccess({ title, body?, lines?, actions? })`: a title only gives a toast, anything more gives a success sheet. Error toasts use the same host |
| useFormFocus, FieldAnchor, FormScrollView | `src/hooks/useFormFocus.tsx` | R2-8 failed-save handling: scroll to the first invalid field, error under it. `useSubmit` (`src/hooks/useSubmit.ts`) ties a submit to it |
| MediaPanel | `src/components/listings/MediaPanel.tsx` | Photos and video on a property and inside active Inspection / Photography visits: camera or gallery (up to 10), Take another, progress, Try again, cover (star), move earlier, delete. Upload via `src/lib/nativeUpload.ts` (direct PUT, then `proxy_url`) |
| MoneyField, formatINR | `src/components/ui/MoneyField.tsx`, `src/lib/money.ts` | Money input with Indian commas and the worded amount below; display as "₹1.25 Crore", "₹50 Lakh", "₹45,000" (Hindi करोड़/लाख) |
| Sector picker (LocalityPicker) | `src/components/leadForm/LocalityPicker.tsx` | Locality Master search (Noida sectors etc.), single or multi; "Other / not listed" free text goes to Ops review |
| LocationField | `src/components/ui/LocationField.tsx`, `src/lib/location.ts` | Full address + "Open Google Maps" + paste a Maps link or "lat, lon" with an instant preview; the server re-parses |
| CallbackPicker, DateTimeField | `src/components/ui/` | 12-hour pickers; callback slots end at 6 PM, with a "customer asked for a later time" exception |
| NotSure | `src/components/ui/NotSure.tsx` | "Not sure" toggle on facts → Ops verification ("Verification pending") |
| CommunicationList / RequirementCommunications | `src/components/lead/CommunicationList.tsx` | Message log behind "Show messages" on each requirement card (status in plain words, Open hidden without a link) |
| RequirementCard | `src/components/lead/RequirementCard.tsx` | Stage, Draft badge, routing (territory AA per area, servicing AA, owner, reason), next action, properties, deal status, messages |
| Notification deep links | `src/lib/deeplink.ts` | `notificationHref(kind, data)` maps every notification kind to a route; `reminderHref(screen, target)` for From Ops reminders. Icons per kind in `src/components/shell/notificationIcons.ts` |
| Push | `src/lib/push.ts` | Registers a token only outside Expo Go; must not load `expo-notifications` in Expo Go on Android |

Notification kinds handled in `deeplink.ts`: `FLOAT_OFFER`, `LEAVE_UPDATE`, `OPS_REMINDER` (ids nested under `data.target` or flat), `KEY_TASK` (collected/returned → that key, otherwise key tasks), `VISIT_UPDATE` (→ that visit), `CUSTOMER_RESPONSE` (visit replies → the visit, else the requirement), `SUPPORT_TICKET`, `EARNINGS_UPDATE`, plus fallbacks on any `relationship_id`, `visit_id`, `listing_id`, `unit_id` or `field_task_id`. A `data.link` starting with `/` wins.

## Data layer
- **Client:** `src/api/client.ts` (`createApi()`, `unwrap()`; Node-safe so the live scripts reuse it), `src/api/instance.ts` (the app instance, tokens in expo-secure-store), `src/api/http.ts` (bearer, single-flight refresh rotation, retry), `src/api/errors.ts` (error envelope → `ApiError` with field errors).
- **Hooks** (`src/api/hooks/`): `auth`, `me` (profile, duty, language, device registration), `config` (`useConfig`, `useLabels`), `leads` (home, relationships, requirements, calls, follow-ups, transfers, referrals, escalations, floats, messages, localities), `listings` (listings, photos, keys, matches, shortlist, visits, no-show, shares, add property, access), `field` (mapping, units, surveys, opportunities, field tasks), `account` (notifications, roster, leave), `reminders` (From Ops, field flags), `phase3` (earnings, My Week, help, tickets).
- **Query keys:** `qk` in `src/api/keys.ts`, `lk` in `hooks/listings.ts`, `fk` in `hooks/field.ts`; a few hooks use inline keys (e.g. `['home']`, `['fieldTasks']`). Mutations invalidate precisely (`invalidateLead`, `invalidateField`, `invalidateAfterSync`).
- **Offline outbox** (`src/offline/`): `outbox.enqueue({ type, entity, entityId, baseVersion, payload, label })`. Allowed types (`OFFLINE_TYPES` in `types.ts`): `survey.create`, `unit_contacts.save`, `unit_details.save`, `listing_draft.create`, `listing_draft.update`, `note.create`, `follow_up.create`, `follow_up.complete`, `key.taken`, `key.returned`. Items replay in order to `POST /sync/batch` (`transport.ts`), idempotent on `client_id`; results are applied / duplicate / conflict (server copy kept for the sync screen, never overwritten silently) / rejected. Sync runs on reconnect, app foreground and every 60 s. Store: SQLite, or memory when ExpoSQLite is missing (Expo Go) or in jest. After sync, `(app)/_layout.tsx` invalidates via `onSynced`.
- Everything else (listing submit, verification, transfers, float claims, visit scheduling, money) needs a connection.

## Glossary
| Term | Meaning |
|---|---|
| AA (Area Ambassador) | Field agent using this app |
| Customer → Relationship → Requirement | One customer (by phone) has one relationship (with an owner AA) and many requirements (BUY, SELL, RENT, RENT_OUT), each with its own stage, servicing AA, properties and next actions |
| Relationship owner (Main AA) | Owns the customer relationship. For AA Add Lead, the creator |
| Servicing AA | Works one requirement. Since R3-3 the creating AA keeps servicing until an explicit transfer |
| Territory AA | The AA covering an area (sector / society). Shown per preferred area (`routing.areas[]`); may differ from the servicing AA |
| Routing reason | Server text explaining why a requirement went to its AA |
| Territory float | A lead in an uncovered area offered to nearby AAs for a limited window; first claim wins |
| SLA | First-contact target (15 min) and breach (30 min) inside service hours 09:00–18:00 |
| Requirement Draft | `is_draft: true` with `missing_fields[]`: saved without required fields (R3-2). Routed, but excluded from matching; "Complete requirement" next action |
| Required requirement fields | BUY/RENT: a preferred locality or Open area, budget/rent (min or max), configuration. SELL/RENT OUT: property type, location, expected price/rent |
| Open area | `area_open`: no area preference; matches widely |
| Mapping vs survey vs unit details vs opportunity vs listing (DEC-01) | Separate records: structure (towers/floors/units); a dated survey snapshot with Owner / Additional / Tenant contact slots; optional extra unit details; a SELL/RENT OUT opportunity from a survey; a marketable listing |
| Listing (property) states | DRAFT → SUBMITTED → CHANGES_REQUESTED → VERIFIED / REJECTED / WITHDRAWN. Only VERIFIED is matched; an AA can't verify their own; submit needs a minimum number of photos |
| Independent property | A listing with no society/unit (house, builder floor, villa, plot), with an address |
| Matched vs Shortlisted | Matched = options the system found; Shortlisted = picked by the AA for this customer, then Share with client |
| Visit types | BUY/RENT: Viewing, Agreement signing, Key handover, Other. SELL/RENT OUT: Inspection, Photography/video, Agreement signing, Key handover, Other |
| Visit outcomes | Per type (`allowed_outcomes`). Viewing: e.g. Interested, Not suitable, Wants to negotiate, Wants another visit, Follow up, No show. Inspection/photo: e.g. Inspection completed, Photos completed, Video completed, More media required. "…completed" needs the media (default 3 photos) |
| No-show | Retained visit outcome: who was absent, optional reason, note, next step Reschedule (new linked visit) / Follow up / Cancel |
| Key custody | Access arrangement on a property (key party, location, mode PER_VISIT or RETAINED). Collect-key task before a visit, return task after a PER_VISIT visit, urgent "Owner wants the key back". Every change is audited |
| From Ops / reminders | Ops sends a reminder to an AA from the admin; it opens the exact record |
| Not sure / Verification pending | AA flags a fact as unsure; Ops confirms or corrects it |
| DNC | Do not contact: calls, follow-ups and messages are blocked (`409 customer_dnc`) |
| Communications | WhatsApp/SMS to customers are **logged only** (no provider yet): status "Queued, not sent" |
| Earnings states | Potential → awaiting fee → eligible → approved → scheduled → paid (UTR). Interim amounts are labelled "Estimate · not final policy" |
